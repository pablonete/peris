# Generate quarterly cashflow

1. Resolve the target data repository (`owner/repo`) and quarter (`YYYY.NQ`, for example `2031.2Q`). Use a repository explicitly named in the request or clear from the current task; if either value is missing, ask for it. The repository must have an `import/` directory with supported Unicaja/Revolut CSVs and an existing `<quarter>/cashflow.json` baseline. Validate the quarter against `^\d{4}\.[1-4]Q$`.
2. Verify `gh auth status`, read access to the target repository, and that it is **private** (`gh repo view "$TARGET_REPO" --json isPrivate`). Stop before cloning or generating if it is public or visibility cannot be verified: cashflow files and row-level import logs may contain private financial data.
3. Check for an open PR already titled `Generate cashflow for <quarter>` in the target repository. If one exists, report its URL and stop instead of creating a competing PR. Read the target repository's default branch.
4. Create a fresh temporary clone of the target repository's default branch and a unique branch `openclaw/cashflow-<quarter>-<UTC timestamp>`. Confirm the clone is clean before running anything. Set `DATA_REPO` to this clone.
5. From the Peris repository root, ensure dependencies are installed with the project's locked pnpm setup if needed. Run:

   ```bash
   PERIS_DATA_REPO_PATH="$DATA_REPO" pnpm --silent run cashflow:generate -- "$quarter"
   ```

   Read the JSON summary. The generator selects exactly one supported statement per bank whose filename range covers the entire quarter; it never combines partial statements, even when their ranges collectively cover the quarter. Partial or overlapping quarter files stop generation before importing. Same-day Revolut rows are ordered from their `Balance` chain; missing or ambiguous chains stop generation. It updates only that quarter's existing `cashflow.json`, never edits/deletes source CSVs, and writes one timestamped `.log.txt` per selected CSV under the target repository's `import/` directory, using the same row-level format as the UI importer. Each log path appears in the JSON summary. Log files are run artifacts and must stay in the target data repository; **never copy or commit them to the public Peris code repository, public PRs, or public issues**.

6. Review `git status --short` and the diff in the target clone. Expected changes are only `<quarter>/cashflow.json` (if its entries changed) and the generated log files in `import/`; no source CSVs, other quarters, or unrelated files may change. Logs contain row-level details, so keep this workflow restricted to the verified private target. Run `git diff --check`.
7. Commit the changed cashflow file, if any, and all logs generated by this run on the target branch. Open a PR against the target repository's default branch titled `Generate cashflow for <quarter>`. Include the CSV basenames, generated log basenames, counts (`created`, `existing`, `ignored`, `sequenceFixed`), and whether cashflow entries changed. Do not copy transaction concepts or amounts into the PR description. Never create a related-issue link unless the user explicitly provides an issue in the target repository. Never merge the PR.
8. Verify the PR URL, head/base, checks, and changed-file list with `gh pr view`; report its link and summary. A run with no cashflow changes still has new timestamped audit logs and may create a log-only PR. If a command fails, reconcile branch/files/PR state before retrying so duplicate entries, overwritten logs, or duplicate PRs are not created.
